## Important implementation decisions

- Keep the project framework-free until the application has enough structure to justify NestJS.
- Use TypeScript's `NodeNext` module mode and compile source files from `src/` into `dist/`.
- LLM construction is provider-agnostic: `LlmService` delegates to a compact `ToolCapableLlm` provider interface, while `FinanceAgent` uses only its common LangChain message/tool-call surface.
- Supported providers are OpenAI (`ChatOpenAI`) and Gemini (`ChatGoogle` from `@langchain/google`). `LLM_PROVIDER` chooses one; unsupported providers fail clearly instead of silently falling back. GLM is intentionally deferred.
- Google's current Interactions API is recommended for new Gemini API projects. The current `ChatGoogle` integration preserves the LangChain tool loop without a FinanceAgent refactor; a direct Interactions API adapter would require deliberately translating the existing LangChain message/tool-result loop and is not justified for the present Phase 1 scope.
- Keep model choice in common `LLM_MODEL`. `OPENAI_API_KEY` is required only for `LLM_PROVIDER=openai`; `GEMINI_API_KEY` is required only for `LLM_PROVIDER=gemini`. `LLM_REASONING_EFFORT` remains OpenAI-only and is not passed to Gemini. Local `.env` files remain ignored by Git.
- The LLM module only invokes a prompt. It has no agent loop, tools, memory, or financial-domain behavior.
- `FinanceAgent` depends on the existing LLM service's tool-enabled message capability and returns `{ text }`, so later tool execution can remain internal without exposing provider-specific response objects to callers.
- `FinanceAgent` remains responsible only for tool selection/execution and its `{ text }` response contract. Google Sheets configuration, authentication-token retrieval, GET-only API access, and debit-ledger mapping are isolated under `src/google-sheets/`.
- The initial HTTP boundary uses Node's built-in `node:http` server rather than a third-party framework, keeping the one-route API dependency-free. It is isolated in `src/http/finance-api-server.ts`, accepts only `POST /api/query`, and depends on the same `FinanceAgent.respond()` contract used by the example.
- The local API listens on port 3001 so it does not conflict with the fixed port-3000 local Google OAuth callback. `npm start` loads `.env` with Node's `--env-file-if-exists` option; no new environment variables are required.
- Application activity logging is isolated behind `ApplicationLogger` in `src/logging/application-logger.ts`. The current console implementation emits scoped `[HTTP]`, `[Agent]`, `[LLM]`, `[Tool]`, `[GoogleSheets]`, and `[Error]` events. Every HTTP request receives a random `queryId` that is carried into the agent and Sheets logs. Completed or failed LLM and tool calls record a millisecond `durationMs`. The logger logs bounded query/event metadata and aggregate expense results, never OAuth tokens, API keys, authorization headers, raw Google Sheets rows, or full LLM system prompts. A later structured logger can implement the same interface.
- FinanceAgent performs a small, bounded LangChain tool-call loop directly. LangGraph is not used.
- `getMonthlySpendingTrend` deliberately groups the existing debit-only `ExpenseDataSource` in TypeScript instead of querying a second Sheets representation or asking the LLM to total transactions. It validates against configured month tabs, deduplicates requested month names, and emits results in configured April–March order. With no requested range, it returns every configured month, including zero-expense template tabs.
- The bounded FinanceAgent loop now registers both `getExpenses` and `getMonthlySpendingTrend`. It retains the request `queryId` in tool logs, records requested month names through the safe tool-argument summary, and logs only aggregate trend metadata (`monthCount`, combined total, and duration), not transaction descriptions.
- `compareSpendingPeriods` takes one or more explicitly ordered labelled periods, each containing one or more configured workbook months, plus an optional literal `categories` filter. It dynamically canonicalizes categories from the current debit data; an unknown category is rejected and never silently changed into an overall-spending calculation. It preserves period order, produces only adjacent period comparisons, and treats month adjacency as calendar order (including December→January and March→April), never the workbook's April–March display order. Percentage change is `(to - from) / from × 100`; when `from` is zero, the structured result is `null` even if `to` is also zero.
- The agent now registers all three expense tools. Its safe comparison logs include compact requested labels/months, `periodCount`, `comparisonCount`, aggregate period total, duration, and inherited `queryId`; they omit transaction descriptions and credentials.
- Phase 3 memory architecture is intentionally split into two future concerns: session-scoped, bounded relevant conversation history for context/reference resolution; and persistent, intentionally created or updated user semantic memory retrieved through embeddings and vector search. Session messages are not automatically persisted as permanent memory, and neither memory type is financial transaction storage.
- Phase 3 also plans item-level expense analysis as a third, separate track. It may inspect individual debit records and their free-text descriptions, but must extend the generic deterministic analysis model rather than create special-purpose item tools. The LLM may select a bounded operation and format its structured result; TypeScript must perform filtering, grouping, counting, aggregation, sorting, comparison, and every financial calculation. The current `analyzeExpenses` does not yet group descriptions.
- Description variations and the lack of a stable transaction ID mean future item normalization/entity grouping cannot silently infer equivalence. It requires a scoped, tested design with clear uncertainty behavior. Financial descriptions/rows must remain out of logs and unnecessary intermediate prompts, and must not automatically become embeddings or persistent user memories.
- GPT-5.6 Terra is configured through `LLM_MODEL`, with `LLM_REASONING_EFFORT=medium` passed to LangChain's OpenAI chat model.
- Local Google OAuth authorization requests use `prompt=select_account` and never send a `login_hint`. When callers explicitly set `reauthorize: true`, the authorization plan marks any saved token ineligible for reuse. The `google-auth` command owns credential loading, callback handling, token exchange, and local persistence.
- The local OAuth callback is intentionally fixed in application code at `http://localhost:3000/oauth2callback`, avoiding privileged-port access. It is not an environment setting. Desktop/Installed OAuth clients use the loopback callback directly and do not require a Web-client authorized-redirect-URI configuration.
- The live inspection used a temporary access token with the Google Sheets read-only scope. No token was saved. The workbook contains account/cash roll-forwards, debt/reimbursement calculations, debit/credit summary matrices, purchase registers, monthly transaction ledgers, and a utility taxonomy; see `WORKBOOK_DATA_MAP.md` for the exact mapping.
- `GOOGLE_SHEETS_SPREADSHEET_ID` is required. `GOOGLE_SHEETS_MONTH_TABS` defaults to the observed April–March order and may select a subset. `GOOGLE_SHEETS_LEDGER_RANGE` is constrained to the observed `A9:G` layout so the reader cannot silently use a different schema.
- The production expense source is built lazily when `getExpenses` runs. Its isolated OAuth layer loads installed-app credentials from ignored `credentials.json` and saved tokens from ignored `token.json`; it never exposes them to the agent or Sheets reader.
- Saved tokens include an expiry time. A token with at least one minute of remaining validity is reused; otherwise the OAuth layer exchanges the refresh token at Google's token endpoint and securely replaces the local token file. Failed or revoked refresh credentials instruct the user to run the forced authorization command.
- The API adapter sends only authenticated `GET` requests with unformatted values and date serials. No write endpoint is present.
- `getExpenses` preserves its name and result shape (`{ expenses, total }`). It maps `sourceSheet` only internally for month filtering, then returns the original public expense fields: date, category, description, and amount.
- The category catalog is not a manually maintained mapping, database, RAG index, embedding store, or semantic-search service. It is derived from distinct current debit labels using the reader's trimming plus the tool's existing case-insensitive exact-match rule. The five-minute in-memory cache avoids a full category-vocabulary read on every agent request; the tool remains the authoritative live validation point.

## Known issues/blockers

- `credentials.json` is present locally and ignored. Its Desktop/Installed client redirect metadata does not need to list the application's fixed loopback callback. Run `npm run google-auth` to create the ignored local `token.json`; reauthorize only if it is missing, invalid, revoked, or intentionally replaced with `npm run google-auth -- --force`.
- The workbook uses free-text account/category labels, yearless date displays, formula-based amounts, fixed-range summary formulas, and no stable transaction IDs. A future reader must map the monthly ledger carefully; see `WORKBOOK_DATA_MAP.md`.
- A live LLM request requires the selected provider's valid API key (`OPENAI_API_KEY` or `GEMINI_API_KEY`); the automated smoke tests intentionally make no external API request.
- Gemini's `gemini-3.8-flash` model identifier is valid and is visible to the configured key. If a 503 persists after the current-provider migration, it should be treated as a provider availability/support issue rather than papered over with agent changes. For inexpensive initial experiments, the available `gemini-3.1-flash-lite` is the better low-cost candidate; reserve `gemini-3.8-flash` for capability-focused tests.
- A controlled live LLM validation still depends on the configured provider being available; all data-layer verification is complete with the existing local read-only workbook access.

## Setup/configuration notes

- Install dependencies with `npm install`.
- Run `npm run typecheck` to check the source, `npm run build` to compile it, and `npm start` to build and start the HTTP API at `http://localhost:3001` with the local `.env` loaded when present.
- Send `POST http://localhost:3001/api/query` with `Content-Type: application/json`, `Authorization: Bearer <API_AUTH_TOKEN>`, and a JSON body such as `{ "query": "How much did I spend on dining out this month?" }`. The success response is JSON with the stable `{ "text": "..." }` shape; missing or invalid authorization receives `401 { "error": "Unauthorized" }`. Run `npm run test:api` to test the HTTP layer without live services.
- Copy `.env.example` to `.env`, set `LLM_PROVIDER` to `openai` or `gemini`, choose a matching `LLM_MODEL`, provide only that provider's API key, and set a long random `API_AUTH_TOKEN`. `LLM_REASONING_EFFORT` applies only to OpenAI. Run `npm run llm:example` to make a live model request, or `npm run test:llm` for the no-request provider smoke tests.
- Run `npm run finance-agent:example` after configuring `.env` to send a user message through FinanceAgent to the live LLM.
- Run `npm run test:expenses` to test the local expense tool. The `finance-agent:example` now asks an expense question and will exercise the tool loop with a configured API key.
- Run `npm run test:google-oauth` to verify local OAuth account selection and intentional-reauthorization behavior without contacting Google.
- Set `GOOGLE_SHEETS_SPREADSHEET_ID` in a local `.env` file. `GOOGLE_SHEETS_MONTH_TABS` and `GOOGLE_SHEETS_LEDGER_RANGE` are documented in `.env.example`; the latter must remain `A9:G` for this workbook schema.
- Run `npm run google-auth` once from the repository root. The command opens the account-selection page where possible and otherwise prints the safe authorization URL. Complete the local callback flow; tokens are stored in ignored `token.json` and never printed. Use `npm run google-auth -- --force` to intentionally choose and authorize an account again.
- No Google Cloud Console redirect-URI update or `.env` OAuth redirect variable is required for the existing Desktop/Installed OAuth client. The application itself uses `http://localhost:3000/oauth2callback` for its local loopback callback.
- Run `npm run test:google-sheets` to verify the Google Sheets data layer without live authentication.
- Future local authorization requires an eligible OAuth account with Viewer access to the workbook. Normal runs reuse the secure local token cache; account selection is needed again only after an invalid/revoked token or an explicit forced reauthorization.
